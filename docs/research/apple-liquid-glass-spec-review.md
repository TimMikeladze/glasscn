# Apple Liquid Glass parity review

Reviewed November 8, 2026. Comparison: `git diff d896a3df956c2c0ad3877b50fa1e0e69f5b09ba8 --`, including the untracked source, tests, showcase and research files present at review time. This is the independent Spec axis. The baseline audits and completion record are evidence to check, not acceptance results.

**The current implementation does not support every public Apple glass interaction one to one.** Native regular/clear material delegates its optics to UIKit; native controls delegate only the supported default prop combinations. Web rendering is an approximation. Several missing interactions are implementable with the installed Expo 57 APIs and browser APIs. They are not blocked by Apple's private compositor.

The initial review records the implementation before follow-up corrections; its line numbers refer to that snapshot. That initial pass changed no product source, ran no install/test suite, and changed no simulator/process state. The dated native re-review appended below records subsequent corrected source and focused test runs.

## Status meanings

| Status | Meaning |
| --- | --- |
| Exact | The stated public interaction contract is present in source. This never means pixel-identical Apple rendering. |
| OS-delegated | The relevant system API renders or manages it. Verification still needs the actual target OS and prop combination. |
| Approximate | A custom implementation reproduces part of the observable behavior. Its geometry, timing or optics differ or remain unmeasured. |
| Missing | The public behavior or usable API is absent or incorrect. A neighboring approximation does not satisfy it. |
| Platform-unavailable | The shipping target or installed bridge does not expose the required API. A new bridge or platform target is needed; this is distinct from a private shader limitation. |

## Findings to implement

### S-01: Native sheets abandon supported system contracts and have incorrect fallback behavior

**Priority: high.** The spec requires “Use native system controls/effects to inherit those defaults” (`docs/specs/apple-liquid-glass-27.md:9`) and native tests that “exercise controlled/uncontrolled custom paths and sheet detents” (`:29`). The detailed source study requires “moving to full height anchors it and makes it opaque” (`docs/research/apple-liquid-glass-2026-11.md:75`) and a nonmodal sheet that “permits related work without dismissal” (`:76`). Apple's [SwiftUI design session](https://developer.apple.com/videos/play/wwdc2025/323/?time=397) describes the material/geometry transition; the [Sheets HIG](https://developer.apple.com/design/human-interface-guidelines/sheets) uses Notes editing as the nonmodal example.

`registry/native/sheet.tsx:93` sends `detent`, `defaultDetent`, `onDetentChange` and `modal={false}` to the custom path. The comment at `:99` says the system reports no detent changes and is always modal. That is false for the installed SwiftUI bridge:

| Installed Expo evidence | Available behavior |
| --- | --- |
| `sandbox/native/node_modules/@expo/ui/src/swift-ui/modifiers/presentationModifiers.ts:27–47` | `presentationDetents(detents, { selection, onSelectionChange })`. |
| `sandbox/native/node_modules/@expo/ui/ios/Modifiers/PresentationModifiers.swift:106–145` | Native selected detent state, notifications, initial selection and updates from a changed selection prop. |
| `sandbox/native/node_modules/@expo/ui/src/swift-ui/modifiers/presentationModifiers.ts:73–95` | `presentationBackgroundInteraction('enabled')`, disabled, automatic, and enabled through a detent. |
| `sandbox/native/node_modules/@expo/ui/src/swift-ui/BottomSheet/index.tsx:16–20,79` | An optional presenting anchor. The current `SystemSheet` at `registry/native/sheet.tsx:131` supplies none. An anchor alone should not be described as a verified zoom/source transition. |

The custom path has three established defects. `modal={false}` still enters `DialogPortal` (`sheet.tsx:229`), which always creates React Native `Modal` (`dialog.tsx:184–186`). Removing the dim does not enable interaction with the presenting screen. Installed React Native selects `overFullScreen` for transparent modals and captures responder handling (`Libraries/Modal/Modal.js:304–308,347`). Render the custom nonmodal inspector in the existing view hierarchy, or use the system sheet's background interaction API.

At a large custom detent, `sheet.tsx:227` computes `large` only for the grabber label. `:159–164` keeps the panel inset; `:234–242` retains regular liquid material and the same radius. The full-height material and edge behavior implemented on web is absent on this native path.

Controlled rejection is also wrong: with `detent={0}`, a drag requesting index 1 calls the callback and then unconditionally springs `rest` to `heights[1]` (`:168–189,202–211`). If the parent retains 0, the effect's accepted `target` dependency did not change, so it does not restore the height. Cancellation has no `.onFinalize` cleanup on this pan. Test accepted, rejected, repeated and cancelled requests with persistent shared values.

Do not assume forwarding the controlled prop to SwiftUI resolves rejection. Expo's `selectedDetent` resets only when `initialSelection` changes (`PresentationModifiers.swift:141–144`). Re-sending the same rejected value does not trigger that change. The wrapper needs an explicit reset strategy or must document/request a bridge fix. Keep custom fallback only for contracts the selected native API cannot honor, such as an asynchronous pre-dismiss veto.

### S-02: Geometry merging is not the complete identity, insertion and union API

**Priority: high for the requested one-to-one scope.** The spec asks for “source transitions” (`docs/specs/apple-liquid-glass-27.md:15`) and to “Rebuild audited navigation, overlay and custom-control defects in both tracks” (`:23`). The source study names “Stable unique `glassEffectID` values and a namespace” and `glassEffectUnion` (`docs/research/apple-liquid-glass-2026-11.md:89`). Apple's [custom-glass guide](https://developer.apple.com/documentation/swiftui/applying-liquid-glass-to-custom-views) distinguishes identity across hierarchy insertion/removal, union membership, and matched-geometry versus materialize transitions.

Web `GlassCluster` has layout spacing and a smooth mask over measured button rectangles (`src/components/glass/glass-cluster.tsx:10–64`). It exposes no stable effect identity, union membership or transition policy. Native `GlassCluster` has only spacing/merge distance and UIKit sibling effects (`registry/native/glass-cluster.tsx:9–38`). `GlassEffectGroup` (`registry/native/glass.tsx:279–296`) does not add SwiftUI identity semantics. The existing demos move permanently mounted siblings; they do not prove insertion/removal identity.

The installed Expo package already supports native identity morphing. `Namespace.tsx:3–7,26–40` provides a namespace; `ios/NamespaceView.swift:12,21` registers an actual `@Namespace`; `modifiers/index.ts:1102–1128` exports `glassEffect` and `glassEffectId`; `ios/Modifiers/GlassEffectModifier.swift:76–85` calls SwiftUI `glassEffectID`. `GlassEffectContainer` is exported at `src/swift-ui/GlassEffectContainer/index.tsx:6–26`. Build a native primitive around those APIs and verify insertion, removal, reordering, interrupted changes and stable identity on iOS.

No `glassEffectUnion` or `glassEffectTransition` wrapper was found in installed `@expo/ui/src` or `ios`. Those are bridge gaps, not unavailable Apple APIs. A narrow native bridge can delegate them to Apple. If a bridge is outside the task, keep those cells explicitly unavailable and do not call geometric merging complete union/transition support.

Web presentation View Transitions at `src/lib/glass-morph.ts:32–97` preserve one trigger/panel identity; they do not supply the separate cluster API. Native custom dialogs/popovers/sheets use offset/scale entrances (`registry/native/dialog.tsx:223`, `popover.tsx:85–97`, `sheet.tsx:224–242`), not matching source geometry. Their effect materialization preserves visibility, but does not establish source-to-presentation continuity.

### S-03: Toolbar resizing, native prominent navigation and native glass buttons are incomplete

**Priority: medium, required for the expanded parity objective.** The spec requires “scroll-responsive bars” (`docs/specs/apple-liquid-glass-27.md:15`) and the six interaction examples (`:24`). The source study additionally specifies visibility priority, explicit overflow and pinned trailing items (`docs/research/apple-liquid-glass-2026-11.md:66`), and standard versus prominent Search (`:67`). Apple's [WWDC26 SwiftUI session](https://developer.apple.com/videos/play/wwdc2026/269/?time=312) demonstrates resize-driven overflow, priority, pinned Share and navigation-bar minimization. Its [search design session](https://developer.apple.com/videos/play/wwdc2026/292/?time=172) distinguishes a search destination from immediate input activation.

Both Toolbar implementations are fixed flex layouts with manually authored overflow children (`src/components/glass/toolbar.tsx:73–115,149–179`; `registry/native/toolbar.tsx:23–57,112–122`). There is no visibility priority, measuring available width to move actions into overflow, or pinned-placement contract. Scaling the toolbar to 90% does not implement the system navigation bar moving out of the way. Keep related action groups together during overflow; preserve keyboard access, selection/focus and pinned commands as width changes.

`GlassTabs` forwards Expo Router's native trigger (`registry/native/tabs-layout.tsx:32–60`), which supplies the legacy `search` role. The installed `expo-router/build/native-tabs/types.d.ts:649` role list has no prominent-tab role. `DockSearch` provides a custom immediate-focus action, but that does not prove a native prominent Search tab. Expose an explicit custom prominent contract and label it, or add an appropriate native bridge. Keep standard Search as a destination without unexpected keyboard focus.

Native `Button` renders custom `Press` plus `Glass`, rather than a SwiftUI Button using system `.glass` / `.glassProminent` styles (`registry/native/button.tsx:98–158`). Its background uses Apple's renderer; its button layout, hit behavior and press motion are custom. Installed `@expo/ui` exposes the SwiftUI Button, `buttonStyle('glass' | 'glassProminent')` (`src/swift-ui/modifiers/index.ts:673–683`) and actual native `.buttonStyle` calls (`ios/Modifiers/ViewModifierRegistry.swift:1750–1763`). A plain supported button path can delegate the full button behavior, keeping custom children/props on an explicit fallback. Do not describe the existing wrapper as the complete system glass button.

### S-04: Supported API knobs and the material inventory need an explicit contract

**Priority: medium.** The spec requires controls to “permit explicit app tint/scheme choices” (`docs/specs/apple-liquid-glass-27.md:15`) and accessible interaction (`:23`). The [Materials HIG](https://developer.apple.com/design/human-interface-guidelines/materials) lists four standard iOS materials. These content materials remain separate from regular/clear Liquid Glass.

Native `GlassIntensity` has three choices (`registry/native/glass.tsx:63`), mapped to ultra-thin, thin and regular materials (`:92–96`). The thick standard material is missing, although installed `expo-blur/src/BlurView.types.ts:87,92,97` supports it. Expose the fourth choice without calling its custom web approximation Apple's numeric material.

`Slider.formatValue` is documented as the spoken value (`registry/native/slider.tsx:38–39`), but the default system-path predicate does not exclude it (`:62–63`) and `SystemSlider` never forwards it (`:75–95`). Only the custom thumb uses it (`:260,317`). Preserve this accessibility value on the native control or select the custom path when requested.

The following options also require accurate capability documentation. Native `LiquidGlass` explicitly discards `optics` and `followLight` (`registry/native/liquid-glass.tsx:5–16`); this is an intentional browser-only option, not a controllable native effect. Native `Glass` intensity and `raised` do not control the iOS Liquid Glass branch (`glass.tsx:188–201`); Apple's effect owns those characteristics. Native plain segmented controls ignore the custom shape choice (`segmented-control.tsx:160–164,219–231`), and `nativeControlTheme` returns a seed color that this community segmented wrapper never consumes. Its installed iOS wrapper destructures appearance and values, without a tint prop (`@expo/ui/src/community/segmented-control/SegmentedControl.ios.tsx:11–29`). Use a direct themed SwiftUI Picker where the requested option is supported, select a custom fallback where needed, or clearly document platform-owned choices.

### S-05: Completion claims overstate coverage of public adaptation and accessibility

**Priority: medium.** The spec says to “Record actual runtime evidence and unresolved limits” (`docs/specs/apple-liquid-glass-27.md:31`). The detailed study names background extension, inactive-window checks and Show Borders/Reduce Bright Effects (`docs/research/apple-liquid-glass-2026-11.md:115–119,159–172`). These are public behavior gaps, separate from unpublished shader coefficients.

The strict matrix below records them. Web materials do not sample backdrop tone or vary scattering/thickness with surface size. Native standard effects handle their own optical adaptation; custom chrome still lacks a window-activity contract. The background-extension helper duplicates content only into a leading strip and cannot represent trailing inspectors or carousel continuation. Native softening is applied only through `web({ filter: 'blur(24px)' })` (`registry/native/sidebar.tsx:79–88`). Sidebars use the whole viewport/window width rather than their own available pane width (`src/components/glass/sidebar.tsx:43–62`; `registry/native/sidebar.tsx:23–27`).

Web has an app-level Reduce Bright Effects option, but no Show Borders option. Native a11y observes only motion, transparency, contrast and bold text (`registry/native/a11y.tsx:13–37`). System controls may honor additional system settings themselves; custom RN decorations have no corresponding observation API. A browser cannot automatically observe all macOS accessibility settings, but a documented app preference can implement the behavior now. Do not silently equate it with OS detection.

The six installable scenes satisfy the named six-scene deliverable. They do not exercise all 20 catalogue examples or all shared component behavior. In particular, web expanded controls are conditionally mounted panels without source identity, and the merge lab moves existing buttons (`src/components/blocks/liquid-glass-01.tsx:225–237`; `src/components/site/liquid-glass-showcase.tsx:53–58`). Web and native use different search patterns and different presentation hosts. The showcase statement that web has “the same ... interactions” (`liquid-glass-showcase.tsx:82`) needs qualification until those specific contracts match.

## Verification and claim corrections

The existing tests substantiate bounded contracts: native mocks inspect effect props; browser tests check displacement and source names; scene tests exercise selected controls. They do not prove native SwiftUI identity insertion/removal, native nonmodal parent interaction, rejected controlled sheet detents, adaptive toolbar overflow, inactive windows, Show Borders or all catalogue examples. `sandbox/native/__tests__/liquid-material.test.tsx:168–186` currently asserts that detent props select the custom path. That assertion encodes the current limitation rather than testing whether the system API can support it.

Revise `docs/native.md:52` and `docs/rules/native.md` when the installed SwiftUI selection/background-interaction APIs are adopted. `docs/native.md:44` overstates explicit palette propagation to the community segmented control. `src/lib/docs.ts:179` says manual reduced transparency gives the same frosts as the OS media query, while the manual path raises clarity and disables optics/highlights, and the media query writes fixed opacity/blur values (`glass-preferences-script.tsx:45–52`; `stylesheet.mjs:506–514`). These are different approximations and should be described by their behavior.

`docs/plans/apple-liquid-glass-27.md` may accurately record completed verification commands, but “all five steps are complete” is not proof of the stronger one-to-one support claim. Keep verified command counts and named runtime observations; record the missing public contracts above until implementation and runtime evidence close them.

No separate scope-creep finding was established. The new showcase, registry entries, shared class helper, source-transition helper and semantic native foreground work serve the stated rebuild. General charts/content logic is not required to acquire liquid effects. AppKit, other Apple platforms and system-owned surfaces need an explicit expanded target before claiming native support.

## Implementation boundary

Implement now: native sheet selection/nonmodal delegation and controlled resets; custom fallback large geometry; formatted slider speech; fourth standard material; direct system glass buttons; native stable identity primitive; responsive toolbar contracts; web app accessibility/activity/size policies. Reuse installed public APIs where they exist.

Add a narrow native bridge or retain explicit unavailability: SwiftUI glass union, explicit glass transition style, native prominent-tab placement/search, presentation zoom source, custom accessibility/window-activity environment observations that Expo does not export. Verify the exact installed SDK before declaring any bridge unavailable.

Keep optical identity claims limited: Apple's kernel, refraction field, spring constants and adaptive coefficient tables are unpublished. CSS/SVG maps, masks, fixed alpha and hand-selected spring values remain approximations even after all public interaction contracts pass. Native system rendering delegates those details; it does not prove custom RN layouts, state machines or presentations match Apple's system controls.
